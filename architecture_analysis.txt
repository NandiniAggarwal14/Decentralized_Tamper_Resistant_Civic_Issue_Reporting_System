===================================================================================
             SYSTEM ARCHITECTURE ANALYSIS: IMPLEMENTATION DOCUMENTATION
===================================================================================
Project: Decentralized Tamper-Resistant Civic Issue Reporting System
Target Context: Springer / IEEE Research Paper System Design Sections

This document contains a comprehensive, reverse-engineered architectural analysis 
of the project codebase. It maps out each layer, process pipeline, and component 
interaction exactly as implemented in the code.

-----------------------------------------------------------------------------------
1. PRESENTATION LAYER (FRONTEND)
-----------------------------------------------------------------------------------
* Technologies: HTML5, CSS3 (Vanilla design tokens in styles.css), Vanilla ES6 
  JavaScript modules, and HTML5 Web MediaRecorder API.
* Communication: Fetch API performing async AJAX queries. Appends JSON or 
  multipart/form-data payloads. Uses Bearer Auth via the headers: 
  'Authorization': 'Bearer <token>'.
* Pages & Roles:
  - index.html: Entrance login/register module.
  - report.html: Citizen console for filing issues, capturing coordinates, 
    and recording audio/video attachments.
  - citizen.html: Feed display, upvote buttons, and stepper timeline track.
  - ward.html: Ward official queue for redirecting complaints.
  - authority.html: Department queue for updating status and uploading proof.
  - admin.html: Account approval controls and blockchain queue recovery logs.

-----------------------------------------------------------------------------------
2. API & SERVICE LAYER (BACKEND)
-----------------------------------------------------------------------------------
* Framework: FastAPI (Python 3.10+) running Uvicorn server processes.
* File Blueprint Structure:
  - main.py: CORS parameters, HTTP headers, static assets paths, and lifespan hooks.
  - config.py: Holds cooldown parameters (30s submission, 5s voting).
  - auth.py: Decodes JWT claims, manages user authentication, and controls 
    RBAC dependency injection modifiers.
  - database.py: Controls psycopg2 ThreadedConnectionPool.
  - helpers.py: Validates file magic bytes, computes SHA-256 hashes, and sorts 
    percentile ranking buckets.
  - routing.py: GIS distance haversine calculator and department mappings.
  - blockchain_service.py: Web3.py Sepolia connector using EIP-1559 gas limits 
    and background worker verification threads.
  - ipfs_service.py: IPFS CID generator and Pinata HTTP client.
  - routes/: Blueprints for auth, issues, ward, authority, admin, and pages.

-----------------------------------------------------------------------------------
3. DATABASE LAYER
-----------------------------------------------------------------------------------
* Technology: Neon PostgreSQL (Serverless cloud-native database).
* Entity-Relationship Tables:
  - users: Enforces UNIQUE username, holds raw plaintext password, role type 
    (CHECK constraint), and is_approved status flags.
  - departments: Holds system departments (e.g. Sanitation, Roads).
  - wards: Geographic ward centers (lat, lng), boundaries, and ward_member_id.
  - government_personnel: Maps official users to specific department ids.
  - category_department_map: Mappings of issue categories to department IDs.
  - issues: Stores details of complaints. Contains user, ward, and department 
    references, CIDs, hashes, upvote counters, and status.
  - issue_votes: Composite key table (issue_id, voter_id) tracking votes.
  - issue_status_history: Audit history trails storing state update comments, 
    proof files, CIDs, and transaction hashes.
  - failed_blockchain_txns: Tracks failed smart contract writes for retries.

-----------------------------------------------------------------------------------
4. BLOCKCHAIN LAYER
-----------------------------------------------------------------------------------
* Network: Ethereum Sepolia Testnet (Chain ID 11155111) via Infura RPC.
* Contract (CivicRegistry.sol): Stores SHA-256 hex digests representing:
  - Issue Hashes: Anchored when a citizen reports an issue.
  - Completion Hashes: Anchored when department officials resolve an issue.
  - Personnel Hashes: Anchored when profile details are modified.
* Payload Construction: Hashed dictionary keys are serialized, ASCII-encoded, 
  and computed using SHA-256:
    D = { id, title, description, category, area, address, latitude, longitude, 
          reporter_name, contact, image_url, created_at }
    Hash = SHA256(JSON.stringify(D_sorted))
* Gas Optimization: dynamic base fee and priority fee calculation (EIP-1559).
* Non-blocking queue: Async background thread checks tx receipt; API responds 
  instantly. Low nonce conflicts are avoided by checking 'pending' tx counts.

-----------------------------------------------------------------------------------
5. STORAGE & IPFS LAYER
-----------------------------------------------------------------------------------
* IPFS Uploads: Uploaded files are saved under uploads/ locally, and pushed 
  to Pinata gateway pinning service (if configured).
* Simulated CIDs: If Pinata is unconfigured/offline, fallback CIDs are 
  constructed locally using:
    CID = "Qm" + SHA256(file_bytes)[:44]
  Files are cached locally at ipfs_storage/{cid}/{filename}.
* References: Backend saves the resulting IPFS CIDs within DB tables, and binds 
  CIDs inside the metadata payloads anchored to the blockchain registry.

-----------------------------------------------------------------------------------
6. SECURITY & ACCESS CONTROL FLOWS
-----------------------------------------------------------------------------------
* Hashing: Currently verified using plaintext comparison.
* Tokens: JWT keys containing subject user UUID and claim roles.
* RBAC Guards: Custom RoleChecker dependencies. Users must be approved 
  (is_approved = True) and match the target role claim to bypass security filters.

-----------------------------------------------------------------------------------
7. COMPLAINT PROCESSING PIPELINE (SUBMISSION)
-----------------------------------------------------------------------------------
Step 1: Citizen fills out report.html, captures coordinates and records attachments.
Step 2: Submits form via POST /api/issues with JWT Authorization headers.
Step 3: API validates inputs (title >= 5 chars, description >= 10 chars, valid GPS).
Step 4: Auto-Routing:
        - Ward: Calculated via Haversine distance to nearest center.
        - Department: Category mapped in category_department_map.
Step 5: Media files are written to uploads/ directory, and CIDs generated via 
        local simulator (or Pinata).
Step 6: Metadata payload is serialized, and a SHA-256 hash computed.
Step 7: Hash is pushed asynchronously to Ethereum Sepolia via Web3.py. Endpoint 
        receives a transaction hash and immediately proceeds without waiting for block verification.
Step 8: Issue details are logged to issues and initial status history tables, 
        and the database commits the transaction.
Step 9: Success JSON response returns to the browser.
Step 10: Background daemon thread awaits mining receipt. If mining fails, logs parameters 
         to failed_blockchain_txns.

-----------------------------------------------------------------------------------
8. COMPLAINT RESOLUTION PIPELINE
-----------------------------------------------------------------------------------
Step 1: Official logs into authority.html and queries active department queues.
Step 2: Uploads resolution proof media and adds completion text comments.
Step 3: Backend saves file, generates IPFS CID, and builds the completion payload.
Step 4: Reconstructs completion hash (SHA-256 of metadata).
Step 5: Calls storeCompletionHash on-chain via Web3.py.
Step 6: Computes status history metadata block, generates a status IPFS CID, 
        and commits the status hash to the Sepolia Registry.
Step 7: Updates issues table state to 'resolved' and adds completion proofs.
Step 8: Inserts audit log step to issue_status_history, database commits, 
        and returns JSON results.
Step 9: Citizen views resolved details on citizen.html; integrity verify can 
        be queried programmatically or using verify_sync_status.py CLI.

-----------------------------------------------------------------------------------
9. DYNAMIC PRIORITY CALCULATION
-----------------------------------------------------------------------------------
* Storage: Upvote/downvote scores are saved inside issue_votes, and denormalized 
  totals are updated on issues table rows.
* Calculation: Executed dynamically inside helpers.py:_assign_dynamic_priorities 
  whenever issues lists are queried.
* Mathematical Percentiles:
    - Top 25% of sorted feed list -> 'critical'
    - 25% to 50% -> 'high'
    - 50% to 75% -> 'medium'
    - Bottom 25% -> 'low'
  This ensures priority maps to community demand, avoiding manual administrative 
  adjustments.

-----------------------------------------------------------------------------------
10. ROUTING LOGIC
-----------------------------------------------------------------------------------
* Ward Determination: Haversine distance formula measures central angles on 
  spherical Earth coordinates to match the closest ward ID center.
* Department Assignment: Mapped through category_department_map query values.
* Staff Allocation: Handled collectively by ward members or department officials 
  assigned to matching jurisdictions.

-----------------------------------------------------------------------------------
11. INTEGRATION DETAILS FOR DIAGRAMS
-----------------------------------------------------------------------------------
* Presentation Layer: Vanilla HTML/CSS/JS, MediaRecorder, i18n, auth.js.
* API Layer: FastAPI Router blueprints (auth, issues, ward, authority, admin, pages).
* Security Layer: JWT Token Authentication, RoleChecker RBAC.
* Logic Layer: helpers.py, routing.py (Haversine distance, percentile priorities).
* Database Layer: database.py pool connector, Neon PostgreSQL cloud instance.
* Storage Layer: ipfs_service.py engine, local uploads/ directory cache.
* Blockchain Layer: Web3.py client wrapper, Sepolia testnet nodes.
* Contract Layer: CivicRegistry.sol mapping hashes.
